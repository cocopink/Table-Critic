# Critique Consolidation 可行性评估

> 用于向老师汇报，2026-04-13

---

## 一、方案概述

基于 Self-Consolidation (arXiv 2602.01966, Yu et al. 2026)，将其核心思想迁移到 Table-Critic 的 Template Tree 上。现有 Table-Critic 的 Curator 机制只存储成功模板、只增不减，我们提出：
1. **对比式模板**：同时积累成功和失败案例
2. **定期巩固**：将相似模板蒸馏为通用知识

---

## 二、可行性分析

### 有利因素

| 因素 | 说明 |
|------|------|
| **有明确的技术参考** | Self-Consolidation 已发表，提供了可参照的 consolidation 范式和评估方法 |
| **现有架构可复用** | Template Tree + Blueprint + Curator 的框架已就绪，改动集中在 `update_tree.py` |
| **改动边界清晰** | 核心改动集中在知识库的存储和蒸馏逻辑，不涉及推理主流程的大幅修改 |
| **直觉合理** | "从失败中学习"和"知识压缩"都是合理的改进方向，故事容易讲 |

### 风险点

| 风险 | 严重程度 | 说明 |
|------|----------|------|
| **失败模板是否有价值** | **高** | Critic 诊断错误或 Refine 修正失败时，存储的"失败模板"可能只是噪声。原论文的 Self-Consolidation 面向 Agent trajectory，失败轨迹天然包含有用信息；但 Critic 的失败诊断可能只是"看错了"，没有可迁移的知识 |
| **Consolidation 蒸馏质量不可控** | **高** | LLM 将多条相似模板蒸馏为一条时，可能丢失关键细节（如特定的错误模式）。无法程序化保证蒸馏质量，只能依赖 LLM 的理解能力 |
| **阈值和触发机制缺乏理论指导** | **中** | 何时触发 consolidation（节点模板数 > N？N 取多少？）、如何定义"相似"（语义相似？error_route 相同？），这些超参数需要大量实验调优 |
| **与现有 pipeline 的耦合** | **中** | Critic 的 few-shot 检索、Blueprint 生成、Controller 路由都依赖现有 Template Tree 结构。引入 success/failure 分类和 consolidation 后，需要同步修改这些下游模块 |
| **实验周期长** | **中** | 需要足够多的样本运行才能积累模板 → 触发 consolidation → 再运行评估。完整的实验闭环可能需要多轮迭代 |

---

## 三、核心疑虑

### 1. 失败模板的信息密度问题

Critic 的失败诊断通常有两种情况：
- **误诊**（错误定位到了错误的步骤）→ 这种失败模板对后续 Critic 没有参考价值
- **正诊但修正失败**（正确定位了错误步骤，但 Refine 没修好）→ 这种情况才有价值，但信息量是否足以形成通用模板？

如果大部分失败属于"误诊"，那么对比式模板的收益会非常有限。

### 2. Consolidation 的收益不确定

原 Self-Consolidation 面向 Agent trajectory，轨迹天然是高信息量的（完整的行动序列 + 环境反馈）。但 Critic Template 中的模板是短文本（几句话的批评示例），信息密度本身不高。对低信息密度的短文本做"蒸馏"，压缩比和效果提升都存疑。

### 3. 与原 Table-Critic 的区分度

原论文的核心贡献是 "critic → refine → iterate" 的闭环框架。我们的改进集中在知识库管理层面（模板存储策略 + 定期压缩）。评审可能认为这是工程优化而非方法论创新。

## 四、建议

| 选项 | 做法 | 风险 |
|------|------|------|
| **A. 直接推进** | 按现有设计实现完整 pipeline，跑实验验证 | 投入大，如果失败模板无价值则前功尽弃 |
| **B. 先做小规模验证** | 手动标注 50-100 个样本的成功/失败模板，人工验证 consolidation 效果 | 投入小，能快速判断方向是否成立 |
| **C. 调整方向** | 放弃 failure template，聚焦 consolidation 对成功模板的压缩效果 | 降低了创新性，但更稳妥 |
| **D. 换方向** | 寻找其他有结构性差异的创新点 | 需要重新调研 |

**本组倾向**：建议先做 **B（小规模验证）**，用 1-2 天时间手动验证失败模板是否有可迁移的知识，再决定是否全面推进。
